## 一、论文 1
### 简介
标题：Synthesizing Inductive Invariants for Distributed Protocols via IC3 and Large Language Models


该论文想解决的问题：
	**如何利用大语言模型，自动为分布式协议生成归纳不变量，从而完成安全性验证。**


这篇论文不是简单地说“LLM 可以做形式化验证”，而是说：
> **LLM 单独做形式化验证不可靠，但如果把它放进 IC3 这种严格的符号验证框架里，让它只负责生成局部候选，再由模型检查器筛选，就能显著提升自动归纳不变量生成能力。**

这也是这篇论文最值得关注的地方：它体现了一种很典型的 **neuro-symbolic** 思路，也就是“神经模型负责启发式生成，符号工具负责严格校验”。


知识点补充：
1. 分布式协议：分布式协议就是多台机器/节点之间协作的规则，比如“谁能当 leader”“什么时候可以 commit”“不同节点看到的状态如何保持一致”。这类协议的 bug 很难靠测试发现，因为错误可能只在某些极端状态组合下出现。论文开头也强调，分布式协议的安全 bug 往往稀有、依赖状态、复现成本高，所以形式化验证很重要。
2. Safety Property，安全性质
	1. 可以简单理解为：坏事永远不会发生
	2. 例如：
		1. 一个 term 里最多只能有一个 primary。
		2. 不能同时有人 commit、有人 abort。
		3. 已经提交的日志不能被低 term 覆盖。
	3. 论文中的 MLDR 例子，安全性质就是 **OnePrimaryPerTerm**，即每个 term 最多一个 primary。
3. **Inductive Invariant**，归纳不变量 
	1. 一个归纳不变量要满足三件事：
		1. 初始状态满足它；
		2. 如果当前状态满足它，执行一步协议动作后，新状态仍然满足它；
		3. 它能推出目标安全性质。
	2. 换句话说，归纳不变量是一种“更强的安全说明”。光写 Safety 往往不够，因为 Safety 可能只描述最终不能坏，但它不一定能排除一些“现在看似没坏、下一步就会坏”的中间状态。论文也明确说，验证安全性通常依赖归纳不变量，而自动推断归纳不变量是主要瓶颈。
4. IC3/PDR
	1. IC3 可以理解成一种**反向堵漏洞**的验证算法。它不是一上来就要求完整不变量，而是维护一系列 frame，逐步找出“可能一步到达坏状态的状态”，然后想办法把这些状态排除掉。论文说 IC3 会维护一系列 reachable states 的 over-approximation frames，并通过发现坏状态、反向找 predecessor、学习 blocking clauses、向前传播 clauses，直到两个相邻 frame 相等，从而得到归纳不变量。
5. Blocking Clause
	1. 一句用来排除坏状态的规则
6. TLA+ state：某一个时刻，协议中**所有状态变量**当前取值的完整快照。


### 论文核心动机：为什么不能直接让 LLM 写完整 invariant
论文用两阶段提交协议做了一个 motivating example。

作者尝试直接让 Claude Opus 4.6 生成完整归纳不变量，然后用模型检查器验证。如果失败，就把反例反馈给 LLM，让它再试。结果在这个协议上，LLM 尝试了 44 次仍然超时，没找到正确 invariant。原因是 LLM 生成的很多 clause 看起来合理，但其中可能混入过强或错误的 clause；完整 invariant 一旦失败，反馈很难告诉 LLM 到底是哪一句错了。

所以这篇论文的关键想法是：

> **不要让 LLM 一次性写完整证明，而是让 IC3 把大问题拆成很多小的 bad-state blocking 问题。**

### IC3Syn 的整体框架

IC3Syn 有三个主要组件：
1. **IC3 Controller**：负责维护 frames、找 bad state、做 predecessor search、管理 clause admission 和 push；
2. **Verification Backend**：用 Apalache 和 TLC 做验证；
3. **LLM Module**：根据协议上下文和 bad states 生成候选 blocking clauses。
![[Pasted image 20260715112413.png]]
图 1 的流程可以这样理解：
> TLA+ 规格输入进来 → IC3 Controller 找到可能导致安全 violation 的 bad state → Apalache 负责符号化 witness 查询 → LLM 根据 bad state 生成 blocking clause → TLC 检查这个 clause 是否会误杀真实可达状态 → 合格的 clause 被加入 frame → 不断迭代，直到 frame 收敛 → 输出 inductive invariant。

---
### Apalache、TLC、TLAPS 分别干什么？

**Apalache**：负责 IC3 loop 里的符号查询，比如“当前 frame 里是否存在一个状态，一步之后会违反 Safety？”以及“这个 bad state 有没有 predecessor？”论文说这些查询本质上是 satisfiability problems，所以用基于 SMT 的 Apalache 处理。

**TLC**：负责批量筛选 LLM 生成的候选 clauses。也就是说，LLM 写出来的 clause 要先在有限可达状态上检查，如果会被真实可达状态反驳，就丢掉。TLC 还会统计每个 clause 能 block 多少 bad states，用来排序。

**TLAPS**：负责最后的严格证明。因为 IC3Syn 的主循环是在有限实例上跑的，不能自动说明无界参数规模也成立，所以作者最后用 TLAPS 证明 29 个 benchmark 中发现的不变量对无界协议实例也归纳成立。

可以记成：
> Apalache 找反例 / witness，TLC 过滤候选 clause，TLAPS 做最终数学证明。

### IC3 与 IC3Syn
针对论文中 IC3Syn 核心步骤的一些理解：

IC3Syn 的核心思想是利用 IC3 将复杂的归纳不变量生成问题拆解为一系列局部的状态阻塞问题，并结合 LLM 的协议语义理解能力生成候选 Blocking Clauses，再由形式化工具对这些 Clauses 进行严格验证。

具体来说，IC3Syn 维护一组对可达状态进行过近似的 Frames (F_0,F_1,\dots,F_k)，其中 (F_0=Init)，非零 Frame 以 Safety 为基础，并通过不断加入经过验证的 Clauses 进行加强。每个 (F_i) 并不表示从 Init 出发至多 (i) 步能够到达的精确状态集合，而是对这些可达状态的过近似，因此其中可能包含实际需要更多步才能到达、甚至完全不可达的状态。

算法首先在当前最深 Frame 中寻找一个 frontier bad state，即该状态本身仍满足 Safety，但执行一步 Next 后可以到达违反 Safety 的状态。找到该状态后，IC3Syn 沿着 Frames 逐层向前寻找其 predecessor。如果能够一直追溯到 (F_0=Init)，则说明存在一条从真实初始状态出发、经过若干次合法 Next 最终到达不安全状态的执行路径，因此得到真实反例，说明系统不满足该 Safety Property。

如果反向搜索进行到某个 (F_i(i>0)) 时，在 (F_{i-1}) 中找不到能够一步到达当前状态的 predecessor，则当前状态成为一个 predecessor-free blocking obligation，说明它虽然被 (F_i) 的过近似包含，但根据当前较浅层 Frame 并不需要被保留，因此需要尝试将其阻塞。此时 IC3Syn 首先查询已有的 Clause Pool，检查之前已经学习到的 Clause 是否能够复用于当前状态。如果存在可复用且能够通过 Admission Check 的 Clause，则直接使用已有 Clause，无需再次调用 LLM。

如果已有 Clause 无法完成阻塞，IC3Syn 才需要尝试生成新的 Clause。与标准 IC3 对每个 predecessor-free bad state 立即进行机械式 Boolean Cube Generalization 不同，IC3Syn 允许 Deferred Blocking：如果当前暂时找不到能够通过验证的 Clause，该未解决的状态会保留在共享 Worklist 中，控制器则继续探索新的 frontier bad states，并进行新的 backward predecessor search。随着探索继续，Worklist 中可能逐渐积累多个相关的、尚未解决的 blocking obligations。IC3Syn 可以将当前 Worklist 中的一批状态共同提供给 LLM，使 LLM 不仅针对单个具体状态生成 Clause，而是根据多个相关失败状态以及完整 TLA+ 协议语义，归纳出更加一般的协议级条件，从而可能用一个 Clause 同时排除一类相关状态。

LLM 每次调用可以生成多个 Candidate Clauses。这些候选不会被直接加入 Frames，而是先经过形式化工具筛选和验证。TLC 用于检查候选 Clause 是否错误排除有限实例中的真实可达状态，并评估 Clause 对当前 bad states 的覆盖能力；Apalache 等符号工具则负责检查 Clause 是否满足相应的 Admission Condition。只有通过验证的 Clause 才会被正式加入相应 Frames，并保存到全局 Clause Pool 中，以便后续处理新的 bad states 或 Clause Push Failure 时继续复用。因此，LLM 在 IC3Syn 中主要负责提出新的协议级候选规律，而 Clause 是否真正成立和能否被采用，仍由形式化工具决定。

IC3Syn 会不断重复“Frontier Query—Backward Predecessor Search—Clause Pool 复用或 LLM 生成—形式化验证—Blocking”的过程。每次成功加入新的 Clause 后，相关 Frames 会被进一步加强，随后重新查询当前最深 Frame 是否仍存在能够一步进入不安全状态的 frontier bad state。只有当当前最深 Frame 中所有这类危险状态都被成功处理，即满足 (F_k\land Next\Rightarrow Safety') 时，当前 frontier 才被认为已经完全阻塞。

在 Frontier Blocking 完成后，IC3Syn 会新增一个以 Safety 为基础的 Frame，并进入 Clause Push 阶段，尝试将已经学习到的 Clauses 向更深 Frame 传播。对于某个 Clause (C)，只有当它满足相应的相对归纳条件，例如 (F_i\land Next\Rightarrow C') 时，才能从 (F_i) Push 到 (F_{i+1})。如果 Push 失败，说明该 Clause 目前还不能在更深层保持成立，**IC3Syn 可以进一步利用 Clause Pool 中已有的 Clauses尝试解决该 Push Failure，必要时再调用 LLM 生成新的候选 Clause**。

经过多轮“寻找危险状态—反向追踪—复用或生成 Clause—形式化验证—Blocking—Push”之后，如果出现两个相邻 Frame 相等，即 (F_i=F_{i+1})，则结合 IC3 所维护的 (F_i\land Next\Rightarrow F_{i+1}')，可以得到 (F_i\land Next\Rightarrow F_i')，说明该 Frame 已经对 Next 封闭。再结合 (Init\Rightarrow F_i) 和 (F_i\Rightarrow Safety)，即可得到一个 Candidate Inductive Invariant。最后，IC3Syn 再使用 TLAPS 对完整的无界 TLA+ 协议进行形式化证明，以确认该候选归纳不变量对任意规模的协议实例都成立。

总体而言，IC3 负责维护 Frames、发现需要阻塞的危险状态、执行 backward search、组织 Blocking 与 Clause Push，并判断何时达到 Fixed Point；Clause Pool 负责保存和复用已经学习到的协议知识；Worklist 负责暂存尚未成功阻塞的 blocking obligations，使多个相关状态能够被批量提供给 LLM；LLM 负责根据一个或多个失败状态以及 TLA+ 协议语义提出新的 Candidate Blocking Clauses；TLC、Apalache 和 TLAPS 等形式化工具则负责筛选、验证和最终证明这些 Clauses。最终，IC3Syn 通过这种“符号搜索确定问题位置、LLM 提出协议级规律、形式化工具保证正确性”的神经符号协作方式，将多个局部 Blocking Clauses 逐步组合并传播，最终形成完整的归纳不变量。
