# Agent 记忆机制：从上下文窗口到长期知识沉淀

Agent 之所以不同于一次性的 Chatbot，一个关键点在于它需要在多轮任务中保持连续性：记住用户偏好、任务目标、已完成步骤、工具执行结果，以及从环境中总结出的可复用经验。这个能力通常被称为 **Agent Memory**。

但“记忆”不是简单地把所有历史消息塞回 prompt。真正可用的记忆系统需要解决三个问题：

1. 什么值得记？
2. 记在哪里？
3. 什么时候取出来用？

## 1. 短期记忆：上下文窗口中的工作台

短期记忆通常对应当前对话或当前任务的上下文。它保存 Agent 正在处理的信息，例如用户刚刚提出的约束、工具调用结果、当前计划和中间推理状态。

短期记忆的优点是读取成本低、上下文相关性强；缺点是容量有限，随着任务变长会被挤出上下文窗口。

工程上常见做法是维护一个工作状态：

```python
working_memory = {
    "goal": "重构博客数据源",
    "constraints": ["不改变视觉效果", "保留 Markdown blog"],
    "completed_steps": ["抽取 projects.json", "抽取 research.json"],
    "open_questions": []
}
```

这种结构比纯聊天记录更稳定，因为它把任务状态显式化了。

## 2. 长期记忆：跨会话复用的知识

长期记忆用于保存跨任务、跨会话仍然有价值的信息。例如：

- 用户偏好：喜欢 Vue SFC、偏好暗色赛博风。
- 项目约定：博客文章放在 `src/blogs/*.md`。
- 反复出现的问题：Windows 与 WSL 共用 `node_modules` 会导致 Rollup optional dependency 冲突。
- 领域知识：Agentic RAG 的核心模块、论文阅读笔记。

长期记忆通常不会直接全部塞进 prompt，而是通过检索召回。常见方案包括：

- 结构化 JSON 或数据库：适合明确偏好、项目配置、状态记录。
- 向量数据库：适合语义检索笔记、文档、经验片段。
- Markdown Wiki：适合人和 LLM 共同维护的知识沉淀。

## 3. 情景记忆：发生过什么

情景记忆关注“某次任务中发生了什么”。它类似事件日志，记录一次任务的过程：

- 用户提出了什么目标。
- Agent 执行了哪些动作。
- 哪些操作失败了。
- 最终采用了什么方案。

这类记忆适合做复盘和避免重复踩坑。例如，当 Agent 以后再次遇到构建失败时，可以回忆到之前的经验：当前项目在 WSL 中运行时，`node_modules` 可能缺少 Linux 原生依赖。

## 4. 语义记忆：抽象后的知识

语义记忆不是记录完整事件，而是从事件中提炼规律。

例如：

```text
在 GitHub Pages 静态站中，不应把 OpenAI API key 直接放到前端。
如果要做 AI 问答，应通过后端代理或构建期生成静态索引。
```

这类记忆更适合长期保存，因为它不依赖某一次具体对话，而是可以迁移到多个任务。

## 5. 程序性记忆：如何做事

程序性记忆保存的是工作流程，也就是“下次遇到类似任务应该怎么做”。例如：

1. 修改 Vue 项目前先检查数据源和路由。
2. UI 调整后检查移动端文本是否溢出。
3. Blog 和 Wiki 内容应通过 Markdown frontmatter 统一解析。
4. 构建失败时先区分源码错误和本地依赖环境错误。

程序性记忆很适合放进 `AGENTS.md`、项目文档或 LLM-wiki 中，让 Agent 在后续任务中复用。

## 6. 记忆写入：不是所有东西都应该记

一个常见误区是“记得越多越好”。实际上，记忆系统最重要的是筛选。

值得写入长期记忆的信息通常满足至少一个条件：

- 未来很可能复用。
- 用户明确表达了偏好。
- 它解释了一个重要决策。
- 它能避免未来重复错误。
- 它是项目或系统的稳定事实。

不适合写入长期记忆的信息包括：

- 临时调试输出。
- 一次性的中间状态。
- 已经过期的假设。
- 没有验证过的猜测。

## 7. 记忆召回：检索比存储更难

存储记忆只是第一步。真正影响 Agent 表现的是召回策略。

一个实用的召回流程可以是：

```python
def recall(query, task_context):
    candidates = vector_search(query)
    filtered = filter_by_project(candidates, task_context.project)
    ranked = rerank_by_recency_and_relevance(filtered)
    return ranked[:5]
```

召回时需要平衡相关性、时效性和可信度。过多无关记忆会污染 prompt，过少记忆又无法发挥长期学习的价值。

## 8. 与 RAG 的关系

Agent 记忆和 RAG 很像，但侧重点不同：

- RAG 更关注从外部知识库中找事实。
- Memory 更关注 Agent 和用户、任务、环境之间形成的连续经验。

在复杂系统中，两者往往会结合：

1. RAG 负责检索文档和知识。
2. Memory 负责保存用户偏好、任务状态和历史经验。
3. Planner 根据召回结果决定下一步动作。

## 9. 一个推荐架构

一个实用的 Agent 记忆系统可以分为四层：

```text
Working Memory      当前任务状态
Episodic Memory     历史任务事件
Semantic Memory     抽象知识与经验
Procedural Memory   工作流和操作规范
```

对于个人知识站或 LLM-wiki，可以先从 Markdown 记忆开始：

- 把稳定知识写成 wiki 页面。
- 把长篇思考写成 blog。
- 把项目约定写进数据文件和文档。
- 让 Agent 每次修改后总结“是否有值得沉淀的知识”。

## 总结

Agent 记忆机制的目标不是让模型机械地保存所有历史，而是让系统能够在合适的时间使用合适的经验。

一个好的记忆系统应该具备三个特征：

1. **选择性写入**：只保存未来有价值的信息。
2. **结构化沉淀**：区分任务状态、事实知识、用户偏好和工作流程。
3. **可控召回**：根据当前任务检索少量高相关记忆。

当记忆机制与 RAG、工具调用、任务规划结合后，Agent 才能从“能回答问题”逐渐走向“能持续协作”。
